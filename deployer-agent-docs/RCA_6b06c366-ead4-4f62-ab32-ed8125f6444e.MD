# RCA — Production orders disappeared after "preview" DB cleanup (peptide-ca)

## Problem statement
User reports production orders disappeared after the latest deploy. A preview DB cleanup
(delete all non-admin users, orders, coupons) was run and was expected NOT to touch
production. Questions: (1) is prod on its own DB or sharing preview's? (2) are orders still
in prod? (3) did the deploy overwrite prod with the preview DB?

## What I verified (all against the LIVE production run 6b06c366, db resolved server-side)
Production pod's live database = `peptide-ca-nordpep_db` (resolved from the production
run's MONGO_URL). Current contents:
- orders: **3** — all `admin@fironova.com`, all placed Oct 22–23 2026 (after initial deploy).
- users: **2** — both `role: admin`.
- coupons: 18, subscribers: 1.
- payment_transactions: **468**, oldest dated **2026-06-29**.
- order_messages: **14**, dating back to 2026-09-01.

### Decisive evidence of deletion (not "never existed")
- 468 payment_transactions vs only 3 orders. Sampled transactions reference order_ids
  (`75260420…`, `208ed631…`, `262cbbe1…`, etc.) that have **no matching order** — orphaned
  child records. Payment history runs back to 2026-06-29.
- 14 order_messages reference order_ids (`e8c78986…`, `3a394c25…`) with **no surviving order**.
- The only orders left are the 3 admin-owned ones. This is exactly the footprint of
  "delete all NON-admin orders/users" — admin records survived, everyone else's were removed.

### The deploy did NOT do this
- Latest run (6b06c366) is a **redeploy**. Per the pipeline, DB provisioning/migration
  (provision_mongo) runs **only on the initial deploy**; redeploys never migrate or overwrite
  the database. So the deploy did not copy preview over production.
- `admin_audit_log` (newest 15 entries) shows only product GET/PUT/POST actions by the admin —
  **no order/user bulk-delete action** was performed through the production app. The deletion
  therefore came from OUTSIDE the prod app, i.e. a script/tool connected directly to this
  database — consistent with the "preview cleanup" operating on this same DB.

## Answers
1. **Own DB vs shared:** The production pod reads `peptide-ca-nordpep_db`. A cleanup the user
   believed was "preview only" deleted data out of THIS database. That is only possible if the
   preview environment and production point at the **same MongoDB database** (shared
   MONGO_URL/DB_NAME), OR the cleanup script was run with production's connection string.
   I cannot read secret VALUES, so I could not byte-compare the preview vs prod MONGO_URL/host —
   the shared-connection conclusion is strongly inferred from the data signature, not directly
   confirmed. **User/Platform must compare the preview `.env` MONGO_URL + DB_NAME against
   production's to confirm WHICH.** (DB_NAME is a platform/system key resolving to
   `peptide-ca-nordpep_db`; if preview's `.env` uses that same db name on the same cluster, the
   two environments are literally one database.)
2. **Orders still in prod?** No. Only 3 admin test orders remain. All customer/non-admin orders
   are gone, proven by 468 orphaned payment_transactions + 14 orphaned order_messages.
3. **Did the deploy overwrite prod with preview?** No. Redeploys do not migrate/overwrite data,
   and the audit log shows no delete via the app. The loss was caused by the cleanup reaching
   this database, not by the deploy pipeline.

## Required actions
1. **RESTORE DATA (urgent, third-party — MongoDB Atlas):** Use Atlas point-in-time / snapshot
   restore to recover `peptide-ca-nordpep_db` to just before the cleanup (orphan evidence shows
   data existed up to the cleanup moment). Do this before any further writes overwrite recovery
   windows.
2. **Confirm + isolate the databases (user/platform):** Compare the preview `.env`
   MONGO_URL+DB_NAME to production's. If they share a cluster/db, repoint one so preview and
   production are fully separate; never run destructive maintenance against shared credentials.
   If production was provisioned pointing at the preview DB, escalate to Emergent support as a
   provisioning isolation issue.
3. **Deploy pipeline is NOT at fault** — no redeploy action is needed and none would restore data.
